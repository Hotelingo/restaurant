# Restaurant Performance Review — v4.3 Operational UX Addendum

**Status:** approved design addendum for Slice 1 implementation  
**Date:** 2026-09-21  
**Baseline:** `wireframe/restaurant-review-wireframe-v4.2.html`  
**Decision:** OD-07

## 1. Purpose and non-negotiable boundary

v4.3 is an **operational addendum**, not an analytical redesign.

The v4.2 six-area customer shell, all analytical screens, Menu MN01–MN12, staff tools ST01–ST04,
reviewer workbench, states, calculations, and the preservation contract remain unchanged.

This addendum supplies the four journeys missing from v4.2:

1. authentication and account recovery;
2. organisation/outlet creation and onboarding;
3. empty/first-run states;
4. error, permission and recovery states.

Production implementation must use the component primitives defined from the v4.2 `STATES` screen.
Do not create a second visual system for onboarding.

---

## 3. Journey A — authentication

### AUTH01 · Sign in

**Goal:** authenticate without exposing tenant information before identity is established.

Required elements:
- product mark/title;
- email;
- password;
- **Sign in**;
- **Email me a magic link**;
- forgot-password link;
- generic invalid-credential message;
- loading and rate-limit states.

Do not reveal whether an email address exists in the system.

After authentication:
1. determine active memberships and staff assignments;
2. enforce MFA when role requires it;
3. resolve last valid organisation/outlet when exactly one is available;
4. otherwise show an organisation/outlet selector;
5. never infer access merely from a URL.

### AUTH02 · Magic link

States:
- link sent;
- link consumed successfully;
- expired/invalid;
- resend cooldown;
- already authenticated.

A magic-link success still proceeds through MFA where required.

### AUTH03 · Invite acceptance

Before acceptance, show only information contained in the signed invitation:
- organisation display name;
- role;
- outlet scope: **all outlets** or the explicitly invited outlet(s);
- inviter display name where safe;
- invitation expiry.

Actions:
- accept;
- decline;
- expired → request a new invite from the inviter/admin.

Acceptance must not allow the recipient to alter role or outlet scope.

### AUTH04 · Password reset

Two stages:
1. request reset link using generic success wording;
2. set a new password after a valid recovery token.

Password UI:
- minimum 12 characters;
- passphrases allowed;
- no composition gimmicks;
- no forced periodic rotation messaging.

### AUTH05 · MFA

MFA is mandatory for:
- `admin`;
- `reviewer`;
- `setup_analyst`.

It is optional for:
- `editor`;
- `viewer`.

The screen must distinguish:
- first enrolment;
- challenge;
- recovery;
- factor unavailable.

A user required to use MFA does not enter the application shell until the required assurance level
is satisfied.

## 4. Journey B — organisation and outlet bootstrap

### Architectural rule

The browser must **not** directly insert the first `organisation` or bootstrap membership.

Use a server-authoritative bootstrap transaction. Recommended contract:

`POST /setup/bootstrap`

Input:
- organisation name;
- organisation slug;
- first outlet name/code;
- reporting currency;
- timezone;
- fiscal-year start month.

Transaction:
1. create organisation;
2. create the authenticated user’s active `admin` membership with `all_outlets` scope;
3. create first outlet;
4. write audit entries;
5. return organisation/outlet identifiers.

If any step fails, none of the bootstrap rows persist.

This avoids the RLS chicken-and-egg problem where the first user cannot receive an organisation
membership until the organisation already exists.

### SETUP01 · Organisation

Fields:
- organisation name;
- URL-safe slug preview.

The slug is a technical identifier. It must not become the customer-visible business name.

### SETUP02 · First outlet

Required:
- outlet name;
- optional outlet code;
- reporting currency;
- timezone;
- fiscal year start month.

R1 permits **multiple outlets in one organisation**, but does not provide consolidated/cross-outlet
reporting. The setup copy must not imply that only one outlet can exist.

One reporting currency is configured per outlet for R1.

### SETUP03 · Context starter

Create `restaurant_context` version 1 using the same vocabulary as SC17:
- service style;
- seats/capacity;
- meal periods;
- business formats;
- important customer sources;
- recipe-costing status;
- labour recording basis;
- source-tracking quality;
- evidence maturity.

The user may skip non-required context fields. Missing information remains missing; it is never
silently converted to a default business fact.

### SETUP04 · First reporting period

Required:
- start date;
- end date;
- label.

Do not ask for P&L values, budget figures or manual financial totals here. Financial data enters only
through the Data Centre ingestion path.

### SETUP05 · Complete

Show:
- organisation;
- outlet;
- reporting period;
- context status;
- next action: **Upload P&L and comparator**.

Primary CTA routes to SC03 Data Centre / Upload Centre.

## 5. Journey C — empty and first-run states

Empty state is a real application state, not an error and not demo data.

### STATE01 · Outlet Home with no period

Show:
- outlet identity;
- setup completion;
- one primary next action: create reporting period;
- secondary link to Restaurant Context.

Do not render zero-valued KPI cards. There is no financial result yet.

### STATE01b · Outlet Home with period but no committed P&L

Show the period header plus:
- “No committed financial data for this period”;
- upload P&L;
- upload comparator;
- data-readiness link.

Again, no zero KPI substitution.

### STATE02 · Data Centre with no files

Show:
- supported R1 templates;
- download-template action where available;
- upload action;
- concise explanation of mapping reuse;
- no percentage readiness score.

### STATE02b · Data uploaded but blocked

Show:
- batch status;
- blocking validation count;
- warning count;
- smallest next action;
- mapping/exception links.

Do not call a blocked batch “failed” when it is recoverable by mapping or source correction.

### Empty search/history states

Packs, issues, actions, and history screens use neutral empty-state copy:
- “No packs generated yet”;
- “No issues shortlisted yet”;
- “No actions recorded yet”.

Never create placeholder rows that look like real customer records.

## 6. Journey D — errors, permission and recovery

### STATE03 · Permission denied

Use for authenticated users who lack the required organisation/outlet/role scope.

Show:
- “You do not have access to this area”;
- current organisation/outlet context where already known to the user;
- return-to-authorised-area action;
- request-access guidance.

Do **not** disclose:
- another tenant’s organisation name;
- whether a guessed outlet/resource ID exists;
- names of users who do have access.

### STATE04 · Recoverable application error

Every unexpected server error must provide:
- human-readable summary;
- retry action where safe;
- correlation ID;
- timestamp;
- support/report action.

Financial mutations must never be blindly retried by the browser. The UI first asks the server for
the authoritative object status. Import commit and later calculation operations must be idempotent.

### STATE05 · Not found / removed

Use the same neutral response for:
- genuinely missing object;
- object outside the caller’s tenant;
- object removed or superseded where the caller cannot view history.

This avoids tenant enumeration.

### Session expiry

On expired authentication:
- preserve the intended route only;
- redirect to sign-in;
- after successful authentication/MFA, resolve access again;
- never preserve an unauthorised object payload in browser state.

## 7. Component/state requirements

All v4.3 screens are composed from the production primitives derived from `STATES`:

- Button
- Field
- Select
- Card
- Table
- Tabs/segmented control
- Chip/status badge
- Disclosure
- Toast
- EmptyState
- Skeleton
- ErrorBoundary panel

Accessibility requirements already recorded in G-44–G-48 apply here from day one:
- full ARIA tab pattern;
- keyboard navigation for composite controls;
- scoped/captioned tables;
- visible field labels;
- accessible disclosures instead of `title` tooltips.

No screen may rely on colour alone for status.

---

## 8. Loading and mutation behaviour

For every form:
- submit action disables only after the request is accepted;
- duplicate clicks must not create duplicate business records;
- return field-level validation separately from server/system errors;
- preserve user-entered non-secret values after recoverable errors;
- never preserve passwords, MFA codes or signed tokens in local storage.

Bootstrap, invite acceptance, context version creation and period creation must all have explicit
success objects returned by the server rather than assuming success from a navigation event.

---

## 9. Acceptance scenarios

The addendum is complete when these scenarios can be implemented without inventing UX during build:

1. New user signs in, enrols MFA, creates organisation/outlet/context/period, then reaches SC03.
2. Invited viewer accepts an all-outlets invitation and lands read-only in the permitted outlet.
3. Invited editor with selected-outlet scope cannot discover or navigate to another outlet.
4. Required-MFA reviewer cannot enter reviewer workbench before challenge completion.
5. Empty outlet displays no fabricated zero financial KPIs.
6. A blocked import points to the remediation path rather than a generic error.
7. A cross-tenant URL returns the same neutral not-found/permission treatment as an unknown object.
8. Session expiry during a form does not leak or persist credentials and returns the user safely.
9. A bootstrap retry cannot create duplicate organisations/outlets.
10. Every unexpected error exposes a correlation ID suitable for audit/support lookup.
